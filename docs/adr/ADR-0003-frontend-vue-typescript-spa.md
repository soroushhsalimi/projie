## Context and Problem Statement

SARA needs a web UI for three very different audiences sharing one codebase: public-ish residents
(browse, apply, track), managers (dense tables, queues, bulk actions, date ranges), and admins (user
management, settings, audit). The UI must be **Persian-first, fully RTL, Jalali-calendar aware**, and
must remain usable on mobile (residents) and desktop (managers).

Constraints:

- The project owner has chosen **Vue.js** and a **FastAPI** backend that already emits an OpenAPI schema.
- One developer builds both sides; contract drift between frontend types and backend responses is a
  realistic and expensive failure.
- The app is a private, authenticated tool — not a content site; SEO and server rendering bring little
  value, while a fast, rich admin experience matters.

The question: what frontend architecture and API-integration strategy?

## Decision Drivers

- End-to-end type safety from FastAPI schema to Vue component props.
- Rich, stateful admin interactions (filters, pagination, dialogs, optimistic updates).
- RTL/Jalali correctness as a first-class concern, not a retrofit.
- Fast feedback for TDD (unit tests in milliseconds; no browser needed).
- Bounded operating complexity for a single maintainer (no SSR server to run).

## Considered Options

1. **Vue 3 SPA (Vite) + TypeScript + generated OpenAPI client**, Pinia + TanStack Query, Vitest + Playwright.
2. Nuxt 3 (SSR/SSG) with the same Vue ecosystem.
3. Vue 3 SPA with hand-written TypeScript API types and `axios`.
4. Server-rendered templates (Django/Jinja) with Vue islands.

## Decision

**We will build a Vue 3 single-page application, bundled by Vite, written in strict TypeScript, and
integrated with the backend through a client generated from the FastAPI OpenAPI schema.**

### Concrete structure

- **Composition API only**, `<script setup lang="ts">`, typed `defineProps` / `defineEmits`.
- **Vue Router 4** with lazy-loaded routes and route-level auth/permission guards.
- **State split:**
  - *Server state* → TanStack Query (Vue Query): caching, retries, invalidation, loading/error states.
  - *Client state* → Pinia: session/auth, UI preferences, multi-step form drafts. No server data is
    duplicated into Pinia stores.
- **HTTP:** `openapi-fetch` + types from `openapi-typescript`, generated by `pnpm gen:api` from the
  committed `openapi.json`. Generation is a CI check: a stale or missing regeneration fails the build.
- **UI:** Tailwind CSS with design tokens + PrimeVue for accessible, RTL-aware primitives (tables,
  date pickers, dialogs). No bespoke date picker, table, or dialog implementation.
- **i18n:** `vue-i18n`, `fa-IR` default, `en-US` secondary; every string via keys; `dir` driven by
  locale; logical CSS properties only.
- **Dates:** transport as ISO-8601 UTC; Jalali conversion confined to `shared/datetime.ts`.
- **Tests:** Vitest + Vue Test Utils for components/stores/composables, MSW for the HTTP boundary,
  Playwright for critical journeys against the real stack.
- **Accessibility:** semantic markup, labeled inputs, focus management, keyboard-operable tables and
  dialogs, WCAG 2.1 AA as the acceptance bar.

## Consequences

### Positive

- **Contract drift becomes a compile error**: a backend field rename fails `vue-tsc` in CI rather than
  producing `undefined` in production.
- No SSR infrastructure to operate; deployment is static files behind a CDN/reverse proxy.
- Rich, fast admin UX without page reloads; TanStack Query removes most hand-written loading logic.
- Vitest runs in milliseconds, so red-green-refactor stays genuinely fast.
- RTL is a global styling decision (`dir`, logical properties), so new screens inherit correctness.

### Negative

- First-load bundle is larger than SSR; mitigated by route-level code splitting and budgets.
- No SEO and no server-rendered meta tags — acceptable for an authenticated tool, blocking if a public
  marketing site is ever needed.
- Two build systems (Python + Node) in one repo; requires pnpm and lockfile discipline.
- Generated client means a backend contract change can break the frontend build immediately — this is
  intended friction, but it requires coordinating both sides in one PR.

### Neutral / Trade-offs accepted

- PrimeVue adds bundle weight; we accept it to avoid re-implementing accessible RTL-aware complex
  widgets (date picker, data table) — a notorious source of bugs and a11y regressions.
- TanStack Query plus Pinia is two state mechanisms; the split is documented (server vs client) and
  enforced in review.

## Alternatives Considered — Why Rejected

| Option | Why not chosen |
|--------|----------------|
| Nuxt 3 (SSR) | Adds a Node server, SSR-specific failure modes, and hydration complexity for zero SEO benefit on an authenticated app. Reversible later if a public site is required. |
| Hand-written API types + axios | Guarantees eventual drift from the FastAPI schema; every endpoint change requires manual type edits; no compiler safety net. |
| Server-rendered templates + Vue islands | Contradicts the chosen stack, gives a worse admin experience, and mixes two rendering paradigms for little gain. |

## Revisit Triggers

- A public, SEO-indexed site becomes a requirement → introduce a separate marketing site or Nuxt, not
  SSR inside this app.
- P95 mobile LCP on the catalog exceeds 2.5 s in the field → revisit rendering strategy or implement
  partial pre-rendering.
- PrimeVue's bundle cost or theming friction exceeds its benefit (measured, not felt) → extract the
  affected widgets into `shared/ui` with headless primitives.

## Verification

- **Automated:** `vue-tsc --noEmit`, ESLint, Vitest in CI; `pnpm gen:api` diff check; bundle-size and
  Lighthouse budgets (F-0403).
- **Review:** no `fetch`/`axios` outside `src/api/`; no server data in Pinia; no hardcoded strings or
  dates in components.
- **Manual:** RTL walkthrough of every new screen; keyboard-only pass.
